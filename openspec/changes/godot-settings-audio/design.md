# Design

## Context

The M5 foundation so far: `GameApi` (typed calls over `LegacyV0Api` or `FakeApi`), the Compatibility API v0 on loopback, the boot scene as main scene, the `ContentRegistry`, `Session`, and `GameClock` autoloads, the camera-controls component, and the UI foundation component — all delivered and archived. Roadmap M5's historical scope (first recorded in `356cc83`) included **Settings** and **AudioManager**, roadmap §17 lists them among the potential autoloads, and AGENTS.md sanctions them as the allowed cross-cutting autoloads, but the M5 Deliver block omits them — this change reconciles the block, and the roadmap ledger names Settings/AudioManager depth as the next eligible M5 objective. Constraints: no new dependencies, loopback-only, pinned engine/interpreter, guard-verified read-only inputs — see proposal.md for motivation and the `godot-settings-audio` deltas for the behavior contract. An evidence search (config keys, save corpus, legacy handlers, SWF inspection symbols) found sound **content** but no legacy user-settings behavior to reproduce, which shapes D2. Three exploration probes were executed against the pinned engine (temporary files, deleted, worktree left clean; nothing committed): (a) under `--headless` with the committed `[audio] driver="Dummy"`, runtime bus creation, naming, send-to-`Master`, mute, and volume mutation all produced observable state with exit 0 and no error output; (b) `ConfigFile` returns `ERR_FILE_NOT_FOUND` (7) for an absent file, a parse error (43) for corrupt contents (printed as an engine `ERROR:` line), `ERR_FILE_NOT_FOUND` (7) for a save into a missing directory, and `0` for a round trip; (c) `func load(...)`/`func save(...)` are legal method names and member-qualified calls (`settings.load(path)`, `self.load(path)`) resolve to them, while an *unqualified* `load(...)` resolves to the global resource loader — so settings.gd only ever calls its own API member-qualified and never unqualified.

## Goals / Non-Goals

**Goals:**
- Two cross-cutting autoload services with explicit committed state, fail-closed envelopes, and change-only signals: `Settings` (two committed preferences plus explicit `ConfigFile` persistence) and `AudioManager` (`Music`/`SFX` runtime buses plus application of the Settings preferences as bus mute), connected by AudioManager's read-only Settings binding.
- Deterministic, hermetic proof in two new suites; the existing scope test enforces the grown boundary (file inventory + exact autoload set).
- A clean spec boundary: two new provisional capabilities record the contracts, and R1 remains the single living allow-list clause, growing to include both systems.

**Non-Goals:**
- No sound or music playback — no `AudioStreamPlayer`, streaming, or triggering API; the 27 extracted MP3s and 139 `sounds` definitions stay untouched content, and the pinned `driver="Dummy"` policy binds with the later sound-content change.
- No settings UI, no automatic load/save, no boot integration (the boot scene's ready flow, session clearing, clock anchoring, and `state=ready` contract stay unchanged).
- No legacy-parity settings claim (no behavioral evidence exists), no M6 work, and no change to the Compatibility API, GameApi, Session, ContentRegistry, GameClock, camera, or UI foundation.

## Decisions

**D1 — Two `Node` autoloads, script-only, registered after `GameClock`.** `scripts/settings.gd` and `scripts/audio_manager.gd` each extend `Node`; `project.godot` registers `Settings` then `AudioManager` after the existing four (registration order is `_ready` order, so Settings is in `/root` before AudioManager binds), and the header comment records them. The scene set stays exactly two — no `.tscn` is added. `[audio] driver="Dummy"` stays exactly as committed since first-render (`569d2bb8`). *Rationale:* AGENTS.md limits autoloads to cross-cutting services and names exactly these two; preferences and audio output are cross-cutting (every future scene consumes them) unlike the scene-owned UI. Keeping the driver avoids behavior churn outside this objective; audible output belongs with sound content. *Alternatives:* scene-owned components (rejected — they would not exist before the first scene and are not scene presentation), one combined service (rejected — AGENTS names two autoloads, and preference state vs. output application are distinct domains), flipping the driver to a real audio device (rejected — changes the verification environment with no sound to play), a `.tscn` per service (rejected — no scene placement exists and it would grow the scene contract for no runtime benefit).

**D2 — Explicitly provisional contract; no legacy claim.** Exactly two boolean preference keys — `music_enabled` and `sfx_enabled`, both defaulting to `true` — exposed through typed accessors (`music_enabled()`, `sfx_enabled()`, `set_music_enabled(bool)`, `set_sfx_enabled(bool)`) rather than a generic key/value dictionary. The proposal records the evidence search (no settings key in `config/main.json`; no settings/sound/music/volume field in the save corpus; no sound/music/settings handler in `command.py`/`engine.py`; only `AudioSheet`/`SpeakerBoxMC` among 1,176 SWFs' exported symbols). The proposal, design, spec Purpose, and README mark the contract provisional while authentic preference semantics (levels, categories, whatever the Flash client had) bind later only if evidence appears. *Rationale:* preservation-first rules forbid inventing legacy behavior; boolean on/off toggles are the minimum neutral state a settings service commits, default-on is the conventional game-audio posture with no evidence either way, and AGENTS.md forbids untyped dictionaries crossing domain boundaries.

**D3 — Fail-closed setters with a change-only signal.** `set_music_enabled`/`set_sfx_enabled` return `{ok: true}` or `{ok: false, error: "setting_unchanged"}` when the request equals committed state; failures leave committed state untouched and are silent; `setting_changed(key, value)` emits once per committed change with the key and new value. Getters reflect only committed state. *Rationale:* mirrors `register_slot`/`set_slot_visible` (rejecting a no-change request instead of absorbing it, so callers can read the getter first) and the house change-only notification discipline (`slot_registered`, `clock_anchored`, `camera_zoomed`). *Alternative:* idempotent success on an unchanged value (rejected — callers could not distinguish "changed" from "already was", and the fail-closed envelope is this project's established pattern).

**D4 — Explicit `ConfigFile` persistence; never automatic.** `load(path := DEFAULT_SETTINGS_PATH)` / `save(path := DEFAULT_SETTINGS_PATH)` over `ConfigFile`, defaulting to `user://settings.cfg`, always called member-qualified (D1 context note (c)). Typed envelopes: `storage_file_missing` when `ConfigFile.load` returns `ERR_FILE_NOT_FOUND`, `storage_read_failed` for any other load failure (corrupt contents — engine parse error 43 — or unreadable file; the message detail carries the engine error code), `storage_invalid_contents` when the file parses but the strict two-key schema is violated (a known key missing, a value not `bool`, or an unknown key present), and `storage_write_failed` when `ConfigFile.save` returns a non-`OK` error. Any failed load leaves committed state untouched (nothing half-applies); a successful load commits both keys and emits `setting_changed` only per key that actually changed; `save` writes the committed state and changes nothing. Nothing loads or saves automatically — no `_ready` persistence, no boot wiring, no signal-triggered write. *Rationale:* `ConfigFile` is the idiomatic typed Godot config API with structured load results and typed `get_value` validation; the strict schema means a file carrying an unknown future key is rejected with state and file untouched instead of silently dropped at the next save (the never-drop-fields preservation instinct applied to our own modern file); keeping persistence explicit keeps suite state machine-independent (an auto-load would make every run depend on the machine's `user://` contents) and the boot flow byte-identical — nothing in the real app persists a preference until the M6 settings panel (or a later change) calls these tested APIs, which the proposal discloses. *Alternatives:* auto-load in `_ready` (rejected — machine-dependent suite state), a generic key/value store (rejected — untyped boundary), a lenient per-key merge (rejected — half-applied state and silent unknown-key drops violate fail-closed), raw `FileAccess` + JSON (rejected — `ConfigFile` gives typed values and structured errors without hand-rolled parsing).

**D5 — AudioManager `_ready`: idempotent bus ensure plus a fail-soft Settings binding.** On `_ready` AudioManager ensures `Music` and `SFX` exist as buses under `Master` (name lookup first, so a re-run or a future default bus layout never duplicates them) and then binds to the Settings autoload through `get_node_or_null("/root/Settings")`: if present, it connects `setting_changed` and applies the current preferences; if absent, it stays operational for direct control (the suite exercises both branches by temporarily removing and restoring the autoload). Settings never references AudioManager — the binding is one-directional. *Rationale:* buses are engine-global output state, not scene state, so the manager owns them from startup; the node-path binding keeps AudioManager instantiable standalone and keeps Settings free of any audio dependency, so a preference service remains usable where no audio consumer exists. *Alternatives:* a `.tres` default bus layout file (rejected — adds a scene-asset artifact to the contract for no behavior gain; runtime creation is testable and idempotent), boot-scene wiring (rejected — would change the boot flow and its suite for integration the manager can do itself), a direct `Settings` global reference (rejected — a parse/runtime hard dependency that breaks standalone instantiation and the fail-soft contract).

**D6 — Bus mute is the enabled mapping; volume policy untouched.** `set_music_enabled(false)` commits and applies `AudioServer.set_bus_mute(music_index, true)`; `true` unmutes; volume is never written (stays 0 dB). Errors: `music_setting_unchanged` / `sfx_setting_unchanged` (request equals committed state) and `music_bus_missing` / `sfx_bus_missing` (the bus was removed externally; rejection leaves committed state untouched). Change-only `music_enabled_changed(enabled)` / `sfx_enabled_changed(enabled)` signals; getters mirror committed state. *Rationale:* mute is the discrete, exactly assertable representation of a boolean preference (probe (a) verified it observable under headless + Dummy), while continuous volume belongs to future level settings with no evidence yet; per-category error names state the exact violated condition (the camera/UI naming discipline), and the bus-missing guard fails safely if someone reshapes buses. *Alternative:* a single `apply(music, sfx)` bulk setter (rejected — per-category envelopes keep failures attributable, mirroring the established per-operation pattern).

**D7 — Ninth and tenth hermetic suites; two scoped source scans.** `tests/test_settings.gd` and `tests/test_audio_manager.gd` use the real autoloads via `/root/` lookups (the session/game-clock suite pattern), ignore the loop's endpoint argument, and join `verify-boot.ps1`'s hermetic list (8 → 10) growing `boot-report.json` by four assertions (52 → 56); neither joins `verify.ps1`. The settings suite covers: startup defaults, commit-once with the `setting_changed` payload, unchanged rejection with untouched state, getters, a save/load round trip over a temp file under `res://.godot/` (repo-local, git-ignored), `storage_file_missing` for an absent file, `storage_invalid_contents` for three schema violations (missing key, non-boolean value, unknown key), `storage_read_failed` for corrupt contents wrapped in `Engine.print_error_messages = false` (the probe proved a corrupt `ConfigFile.load` prints an engine `ERROR:` line that `verify-boot.ps1`'s `^ERROR:` scan would fail on — the flag is restored immediately), change-only emission across a load, and `storage_write_failed` for a save into a missing directory. The audio suite covers: both buses ensured at startup under `Master`, unmuted defaults and default getters, the live Settings → AudioManager binding (signal payload plus bus state), each setter's commit, unchanged rejection, `*_bus_missing` (bus removed and restored inside the suite), the fail-soft absent-Settings branch with restoration, and the initial-apply change-only discipline. Source scans: the settings suite forbids the camera's 16 tokens **minus** `ConfigFile` and `load(` (both are the sanctioned persistence mechanism — `config.load(path)` is literally `ConfigFile.load`) **plus** `ResourceLoader`, `AudioManager`, and `AudioServer` (17 tokens — content loading stays guarded by `preload(` and `ResourceLoader`; the preference service keeps no audio dependency); the audio suite uses the camera's exact 16 tokens (its `/root/Settings` reference is allowed because `Settings` is not a forbidden token, and it has no persistence, so `ConfigFile`/`load(` stay forbidden there). Transport and legacy tokens remain covered by the project-scope scan of every allow-listed file. *Rationale:* `godot-camera` D8 and `godot-ui-foundation` D7 established that client-component suites live in `verify-boot.ps1`, and the two token-list deviations are forced by the sanctioned mechanism and disclosed rather than hidden.

**D8 — Scope contract growth and spec-boundary ownership.** `test_project_scope.gd`: `ALLOWED` += the four new files (43 → 47); `EXPECTED_AUTOLOADS` += the `Settings` and `AudioManager` lines (4 → 6) with its count/message assertions and header comment updated; `EXPECTED_SCENES` unchanged; `FORBIDDEN` unchanged at the 13 legacy/transport tokens (neither new service touches them — no token retires, unlike `UiFoundation`). Spec boundary: `first-render-in-godot` R1 is the single living allow-list statement and is MODIFIED here (the settings and audio work joins the allow-listed foundation systems; the scenario's list becomes the six allow-listed autoloads); the per-change containment requirements of earlier capabilities (`godot-session`: three autoloads, `godot-content-registry`: two, `godot-game-clock`: four, `godot-camera`: 41 files, `godot-ui-foundation`: 43 files/four autoloads) record their own change's boundary and remain historical, as established by those changes and accepted by the independent verifier.

**D9 — Docs and records.** The `project.godot` header comment records the two new autoloads; `AGENTS.md` and `apps/client-godot/README.md` describe the actually executed ten-suite battery with observed counts plus each new suite's coverage and envelope table; the regenerated `boot-report.json` is committed as `test:` per established convention; the roadmap M5 Deliver block gains the `Settings` and `AudioManager` lines in this proposal stage (reconciliation of the milestone list with the historical M5 scope), and the Project Status ledger is updated at archive (root-orchestrator-owned).

## Risks / Trade-offs

- [Corrupt-file test trips the `^ERROR:` log scan] → the suite wraps only that `ConfigFile.load` in `Engine.print_error_messages = false` and restores it in the same block; the probe proved both the error line and the missing-file silence, and every other tested failure path prints nothing (probe-confirmed for absent files and save-to-missing-directory).
- [Settings source scan drops `ConfigFile` and `load(` tokens] → forced by the sanctioned persistence mechanism; content loading stays guarded by `preload(` and `ResourceLoader`, the wall-clock, other-persistence (`FileAccess`, `DirAccess`, `ResourceSaver`), and other-autoload (`GameApi`, `ContentRegistry`, `Session`, `GameClock`, `AudioManager`, `AudioServer`) guards remain, project-scope still scans both new files for all 13 legacy/transport tokens, and the settings.gd diff is bounded by this change — disclosed in D7.
- [Provisional preference contract mistaken for parity] → proposal, design, spec Purpose, and README all label the contract provisional and bind authentic semantics to a later change that captures evidence first; no scenario claims legacy behavior.
- [Services delivered but unused at M5] → deliberate and disclosed: no HUD exists to host a settings panel, nothing outside the suites calls the setters or `load`/`save` yet, the suites are the executable proof, the M6 HUD consumes both, and the M5 exit criterion ("Client boots and communicates with Compatibility API") does not depend on them.
- [Temporary autoload mutation in the audio suite] → the removal window is synchronous and restoration is asserted (`Settings` back at `/root/Settings`, buses restored to unmuted defaults), and each suite runs in its own process so no other suite can observe the mutation.
- [Second consecutive re-touch of R1] → R1's general clause was written to absorb exactly this growth; the delta changes only the enumerated systems and the autoload count, and the scope test enforces the six-autoload set exactly, so no system outside the allow-list can appear.
- [Boot-report/evidence churn] → regenerated by the verification run and committed as `test:` with provenance noted; first-render evidence and all guarded bytes stay byte-identical (they are not inputs to this change).

## Migration Plan

Additive only — no state to migrate, no rollback beyond removing the four allow-listed files, reverting the scope/verify/doc edits, and removing the two autoload lines. No OpenSpec-unspecified behavior changes.
