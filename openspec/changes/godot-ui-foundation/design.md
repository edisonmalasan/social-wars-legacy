# Design

## Context

The M5 foundation so far: `GameApi` (typed calls over `LegacyV0Api` or `FakeApi`), the Compatibility API v0 on loopback, the boot scene as main scene, the `ContentRegistry`, `Session`, and `GameClock` autoloads, and the camera-controls component — all delivered and archived. Roadmap M5 lists **basic UI foundation** next (then Settings/AudioManager depth), and `first-render-in-godot` R1 currently forbids UI foundation in the project until its own change adds it. Constraints: no new dependencies, loopback-only, pinned engine/interpreter, guard-verified read-only inputs — see proposal.md for motivation and the `godot-ui-foundation` delta for the behavior contract. An evidence search (config keys, save corpus, fixtures, SWF inspection symbols) found UI content but no legacy UI behavior or structure to reproduce, which shapes D2.

## Goals / Non-Goals

**Goals:**
- One reusable UI-foundation component with explicit committed state (layer index + an ordered named-slot registry), fail-closed management envelopes, change-only signals, and pointer pass-through containers — the layer the M6 town/HUD scene will instance.
- Deterministic, hermetic proof of the component in its own suite; the existing scope test enforces the grown boundary.
- A clean spec boundary: R1 remains the single living allow-list clause and moves the UI foundation from the absent list to the allow-listed work.

**Non-Goals:**
- No legacy-parity UI behavior (slot taxonomy, z-order, HUD layout) — no behavioral evidence exists, and capturing it belongs to the HUD/UI work before any parity claim.
- No HUD content or widgets: no labels, buttons, themes, fonts, colors, tooltips, dialogs, cursor, selection, or menus — only the slot mechanism.
- No boot/scene integration (the boot scene keeps its own status labels), no autoload changes, no scene-set changes, no API/compatibility changes, no Settings or AudioManager work.

## Decisions

**D1 — A `CanvasLayer` scene-node component, not an autoload.** `scripts/ui_foundation.gd` extends `CanvasLayer`; it is script-only (no new scene file) and instanced where the game UI lives — the M6 town/HUD scene. *Rationale:* AGENTS.md limits autoloads to cross-cutting services (`GameApi`, `Session`, `ContentRegistry`, `GameClock`, `Settings`, `AudioManager`); UI is presentation owned by the scene that shows the game, and boot has no game UI yet. `CanvasLayer` is the correct root because it draws on its own canvas with an identity transform (independent of the camera's canvas transform) at an explicit layer index above world content — exactly what a HUD overlay needs. Consequence: this is the second M5 change that does not grow the autoload set (stays exactly four) or the scene set (stays exactly two). *Alternatives:* fifth autoload (rejected — not cross-cutting and dead at startup), a `Control` root in the world canvas (rejected — no explicit layer ordering above future world layers), a `.tscn` scene file (rejected — nothing would place it, and it would grow the scene contract for no runtime benefit; the M6 scene can wrap the script if editor placement is wanted).

**D2 — Explicitly provisional contract; no legacy claim.** The proposal records the evidence search (no UI structure key in `config/main.json`, no UI state field in saves/fixtures, UI-content symbol families in the SWF inspection that carry no timeline semantics or behavior). The component therefore specifies a neutral, testable foundation — named overlay slots registered at runtime, registration-order stacking, full-rect pass-through containers — and the proposal, design, tasks, and client README mark the structure provisional while the spec's Purpose explicitly disclaims legacy-parity UI behavior. *Rationale:* preservation-first rules forbid inventing legacy behavior; later HUD/UI work captures authentic UI evidence before binding parity. The symbol inventory proves UI content exists (buttons, popups, tooltips, panels) but is a static name/ID inventory with no layout or interaction semantics — content evidence, not behavior evidence.

**D3 — Fail-closed `{ok, error}` management envelopes.** `register_slot()` fails with `slot_empty_name` / `slot_already_registered`; `set_slot_visible()` fails with `slot_not_registered` / `slot_visibility_unchanged`; every failure leaves committed state untouched and is silent. *Rationale:* mirrors `ContentRegistry.load_content()` / `Session.activate()` / `GameClock.anchor()` / the camera's `zoom_in()` / `pan_by()` so callers handle failure uniformly; rejecting an unchanged visibility matches the camera's rejection of a zero pan — a no-change request is reported, not absorbed, and the caller can read `is_slot_visible()` first; rejection silence matches the house notification discipline. *Alternative:* idempotent success on an unchanged value (rejected — callers could not distinguish "made visible" from "was already visible", and the fail-closed envelope is this project's established pattern).

**D4 — Registration-order slots with full-rect pass-through containers.** Each successful registration appends a `Control` child named for the slot: full-rect anchored, `mouse_filter` set to pass-through (`IGNORE`), starting visible. Tree order is registration order and therefore paint order — later slots draw above earlier ones. *Rationale:* exact assertions with no z-index arithmetic, and the pass-through default guarantees the foundation never eats pointer input destined for the world or camera once integrated; interactivity is opt-in per widget a consumer adds inside its slot. *Alternative:* a fixed built-in slot taxonomy (`hud`, `dialogs`, `tooltips`, `cursor`) with names derived from the observed symbol families (rejected — even though the SWF symbol names suggest such categories, fixing them would bake an unevidenced M6 structure into the foundation; registration order defers the taxonomy to the change that captures evidence).

**D5 — Committed layer-index constant.** `UI_LAYER_INDEX` is a script constant equal to the `CanvasLayer` default (`1`); the node's own `layer` is set from it at creation and the suite asserts agreement, mirroring the camera's factor/node-zoom agreement. *Rationale:* explicit committed state beats an implicit engine default; the value sits above default world canvas content (layer 0) with no evidence either way, so the engine-default value is the neutral choice. *Alternative:* a headroom value such as 10 (rejected — equally unevidenced, and it would silently claim a layering scheme the M6 world change has not specified).

**D6 — Two change-only signals.** `slot_registered(slot_name)` once per successful registration with the slot name as payload; `slot_visibility_changed(slot_name, visible)` once per committed visibility change with the new value as payload. Rejected requests and unchanged-value requests are silent. *Rationale:* the house transition/advance discipline (`clock_anchored`, `session_activated`, `camera_zoomed`) lets later systems (HUD, dialogs) subscribe without polling.

**D7 — Eighth hermetic suite in `verify-boot.ps1`; no boot integration.** `tests/test_ui_foundation.gd` needs no API, no service, and no boot flow; it joins the hermetic loop (which passes the endpoint argument that this suite ignores), growing that list from seven to eight and `boot-report.json` by the suite's two assertions. It does not join `verify.ps1`, which remains the render/content battery. The suite covers: the empty start, successful registration with container and ordering assertions, both registration rejections, hide/show with change-only notification assertions, both visibility rejections, the layer-index agreement, and a direct source scan of `ui_foundation.gd` for the scaffold's no-clock/no-persistence/no-loading/no-other-script clauses (the camera suite's token list), since transport and legacy tokens are covered by the project-scope scan of every allow-listed file. *Rationale:* `godot-camera` D8 established that client-component suites live in `verify-boot.ps1`, and boot-scene assertions are untouched because nothing in the boot flow changes.

**D8 — Scope contract growth and spec-boundary ownership.** `test_project_scope.gd`: `ALLOWED` += `scripts/ui_foundation.gd`, `tests/test_ui_foundation.gd` (41 → 43); `EXPECTED_AUTOLOADS` unchanged at the four lines; `EXPECTED_SCENES` unchanged at `boot.tscn` + `first_render.tscn`; `FORBIDDEN` drops `"UiFoundation"` (count assertion 14 → 13) — the token stops marking a deferred system now that the system exists (same precedent as the `Camera2D`/`Camera3D` retirement), and the file inventory bounds where UI code can live, while the legacy-protocol and non-loopback transport tokens remain. Spec boundary: `first-render-in-godot` R1 is the single living allow-list statement and is MODIFIED here (the UI foundation joins the allow-listed work; the named absent list disappears and the clause becomes "every system outside this allow-list"); the per-change containment requirements of earlier capabilities record their own change's boundary and remain historical, as established by `godot-session`, `godot-game-clock`, and `godot-camera` before it.

**D9 — Docs and records.** The `project.godot` header comment retires the "UI foundation is the only game system still deferred to its own change" line in favor of the completed-foundation statement; `AGENTS.md` and `apps/client-godot/README.md` describe the actually executed eight-suite battery with observed counts; the regenerated `boot-report.json` is committed as `test:` per established convention; the roadmap Project Status ledger is updated at archive (root-orchestrator-owned).

## Risks / Trade-offs

- [`UiFoundation` retirement weakens the forbidden list] → the remaining 13 tokens still exclude every legacy protocol and non-loopback transport primitive; the `ALLOWED` inventory still bounds where UI code can live (only `scripts/ui_foundation.gd` and its suite); the autoload and scene sets are enforced by their unchanged assertions; the residual risk of UI code smuggled into another allow-listed file is bounded by this change's diff plus the per-file forbidden-token scan.
- [Provisional slot structure mistaken for parity] → proposal, design, spec Purpose, and README all label the structure provisional and bind authentic UI structure to later HUD/UI work that captures evidence first; no scenario claims legacy behavior.
- [Component delivered but unused at M5] → deliberate and disclosed: no game world exists; the suite is the executable proof, and M6 instances the component into the town/HUD scene; the M5 exit criterion ("Client boots and communicates with Compatibility API") does not depend on it.
- [Pass-through default surprises interactive consumers] → documented contract: containers never intercept pointer input; interactivity is opt-in per widget, and the suite asserts the default so a silent change to `STOP` would fail loudly.
- [Boot-report/evidence churn] → regenerated by the verification run and committed as `test:` with provenance noted; first-render evidence and all guarded bytes stay byte-identical (they are not inputs to this change).

## Migration Plan

Additive only — no state to migrate, no rollback beyond removing the two allow-listed files, restoring the `UiFoundation` token, and reverting the doc prose. No OpenSpec-unspecified behavior changes.
