# Proposal

## Why

M6 proved a player can launch and view a real legacy town without Flash, but nothing yet lets a player *change* that town: the Compatibility API v0 is read-only by contract, `GameApi` exposes only boot operations, and no modern path has ever executed a legacy gameplay command. M7 begins with its first roadmap deliver line, **placement**, and the smallest coherent bounded objective in roadmap order is the full placement slice — the player picks a building, previews its footprint on the grid, and places it, with the mutation executed by the unchanged legacy command path and persisted with executed-legacy parity.

## What Changes

- **Executed-legacy placement fixture**: capture a real `command.php` `buy` transaction (request, before/after save state, response) by executing the real legacy server inside a disposable copy under the pinned interpreter, commit it under `tests/fixtures/godot-building-placement/` with a manifest and README (command, exit codes, containment) — the parity oracle for placement, following the executed-legacy boot-fixture pattern.
- **Compatibility API v0 placement execution**: a new loopback JSON endpoint that accepts a placement **intent** (save id, building id, grid coordinates, orientation) — never client resource deltas — synthesizes the legacy `buy` command envelope internally (price derived from the item's config `costs`, next free map slot, player team 1), executes the unchanged legacy `command()` dispatcher in-process (resource application with legacy clamping, `map_add_item` attribute rules, `bought_unit_add`, batch `save_session` persistence into the corpus), and answers with the legacy response plus an authoritative state superset (the persisted placement entry and current resources) in a documented envelope; structurally unresolvable input fails closed with structured JSON errors; the bootstrap/session read-only guarantee is preserved and working-tree saves are never written.
- **GameApi placement operation**: a typed `place_building()` operation on the `GameApi` autoload with two interchangeable implementations — `LegacyV0Api` speaking loopback JSON to the new endpoint and `FakeApi` a deterministic in-memory double over committed fixture data — with presentation code still never touching transport, legacy URLs, form encoding, or legacy command names (the scope test keeps its forbidden-token contract).
- **Client placement flow**: a build picker over a typed placement catalog parsed fail-closed from the bootstrap config the client already receives (store-listed buildings gated by `min_level` against the loaded level), a footprint preview at the inverse-projected cell with client-side validity — grid bounds, occupied tiles, affordability display — mirroring the validation the Flash client must have performed since the legacy server never validates, confirm sends the intent, and success applies the authoritative response: the new depth-sorted object renders and HUD resources update from the response, never from client-computed deltas; a failed request surfaces an explicit error and changes nothing.
- **Verification**: offline fixture-replay parity tests (no server, no network), fail-closed and persistence tests at the endpoint, GameApi fake/live placement tests, new headless placement suites registered in both batteries, updated project-scope allow-list, a committed windowed evidence capture plus a deterministic structural report with explicit non-claims, preservation guards and the hash manifest green, and the actually executed commands documented in `AGENTS.md` and the READMEs.

Legacy sources, configs, saves, villages, fixtures, conversion packages, and registry manifests stay byte-identical (existing SHA-256 guards plus the hash manifest). The legacy `buy` command fuses payment and placement, so the cost is applied exactly as that legacy path applies it; the separate M7 purchase flows (`buy_si_help`, stored/cash purchases, shop surface) remain open deliver lines.

## Capabilities

### New Capabilities

- `godot-building-placement`: the end-to-end placement slice — the executed-legacy placement fixture and its parity claim, the v0 placement execution endpoint (intent contract, derived envelope, legacy execution, persistence, fail-closed errors), the typed `GameApi` placement operation with both implementations, the client picker/preview/validation/confirm/apply flow, committed evidence with claim limits, and containment.

### Modified Capabilities

- `godot-compatibility-boot`: re-scope the "never persists state" guarantee to the session and bootstrap endpoints (placement execution persists by unchanged legacy command semantics into the corpus only, per the new capability), and extend the GameApi abstraction requirement with the typed `place_building()` operation alongside `list_sessions()` and `get_bootstrap()`; the headless boot contract, fixtures, and parity requirements are unchanged.

## Impact

- **Code (new)**: Compatibility API placement route module and its tests, `apps/compat-api` placement fixture-capture tooling and `tests/fixtures/godot-building-placement/` (request/before/response/after + manifest + README), client placement scripts (typed catalog, picker/preview, placement flow) and `tests/test_town_placement*.gd` suites, `apps/client-godot/evidence/placement/` captures and report.
- **Code (edited)**: `apps/compat-api/compat_service.py` (route wiring), `scripts/gameapi/game_api.gd`, `fake_api.gd`, `legacy_v0_api.gd` (operation), `scripts/town/town.gd` + `scenes/town.tscn` (placement mode), `tests/test_project_scope.gd` (allow-list), `verify-boot.ps1` (suite registration), `apps/client-godot/README.md`, `apps/compat-api` README, `AGENTS.md` (commands actually executed).
- **Read-only legacy inputs consumed**: `config/main.json` item fields (`costs`, `min_level`, `in_store`, `width`/`height`, `type`), legacy `command.py`/`engine.py`/`sessions.py` executed unchanged in-process, `tests/saves/fresh-player.json` as the capture seed — all byte-identical before and after.
- **Unchanged**: legacy server behavior and protocol, the bootstrap contract (still read-only, still one bootstrap per launch), ContentRegistry, camera/session/settings/audio, M4 and M6 evidence bytes, conversion and registry tooling, `tests/saves/*`.
- **Dependencies**: none added — Godot 4.7.2 and pinned CPython 3.9.13 only.
- **Claim limits carried forward**: the price vector, envelope placeholders (`reason`, `unknown`, `accessToken`), slot choice, and the Flash client's exact placement-validation rules are derived — the Flash client is never executed, so its client-side delta vector and validation behavior are unobservable; parity covers one recorded `buy` transaction against the fresh-player corpus, not progressed-player coverage; insufficient resources reproduce legacy clamping (max 0), never rejection — server-side economy validation belongs to Server v1 (M13); no pixel-parity oracle exists, so evidence is structural plus committed captures.
