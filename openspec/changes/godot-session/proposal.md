# Proposal

## Why

The boot scene currently owns the selected session (which save was bootstrapped, and its typed summary) as scene-local state that disappears with the scene, so no later foundation system (UI, clock, settings) can observe who is logged in without reaching into boot internals. M5's autoload plan (roadmap §17) reserves `Session` as the cross-cutting holder for exactly this state; with GameApi, the Compatibility API v0 bootstrap slice, and ContentRegistry delivered and archived, the Session scaffold is the next bounded M5 objective.

## What Changes

- New `Session` autoload (`apps/client-godot/scripts/session.gd`): a pure state holder for the active session — explicit `activate(user_id, summary)` / `clear()` lifecycle returning `{ok, error}` with fail-closed validation, typed getters (`is_active`, `user_id`, `summary`), transition-only signals, and no implicit session at startup.
- Boot integration: the boot scene clears any previous session before each boot attempt and activates it after a successful bootstrap, so a failed boot can never leave a stale session behind.
- New headless suite `tests/test_session.gd` wired into `verify-boot.ps1`'s hermetic list (scaffold lifecycle scenarios plus boot integration), and boot-scene assertions extended to cover the session at ready and after failures.
- Project scope grows: `project.godot` declares a third autoload; `test_project_scope.gd` allow-lists the two new files, expects exactly three autoloads, and drops the `Session` forbidden token (18 → 17) while every other forbidden enumeration (GameClock, camera, UI foundation, legacy protocol, non-loopback transport) stays forbidden.
- Documentation: `AGENTS.md`, `apps/client-godot/README.md`, and boot-verification docs record the executed commands and suite counts; the roadmap Project Status ledger is updated at archive time.

## Capabilities

### New Capabilities

- `godot-session`: the Session autoload scaffold — explicit session lifecycle with fail-closed activation, boot-scene integration that populates and clears the session, and containment of the grown project scope.

### Modified Capabilities

- `first-render-in-godot`: requirement R1 "Minimal render-verification Godot project" — the foundation allow-list grows to include the `Session` autoload with its script and tests, the project declares exactly three allow-listed autoloads (`GameApi`, `ContentRegistry`, `Session`), and the forbidden enumeration drops `Session` while GameClock, camera, and UI foundation remain absent.

## Impact

- New files: `apps/client-godot/scripts/session.gd`, `apps/client-godot/tests/test_session.gd`.
- Modified files: `apps/client-godot/project.godot` (third autoload), `apps/client-godot/scripts/boot.gd` (clear/activate integration), `apps/client-godot/tests/test_boot_scene.gd` (session assertions at ready and on failure), `apps/client-godot/tests/test_project_scope.gd` (allow-list, three-autoload expectation, forbidden-token list), `apps/client-godot/verify-boot.ps1` (hermetic suite + report wiring), `apps/client-godot/README.md`, `AGENTS.md`, and the roadmap Project Status ledger at archive time.
- Evidence: `apps/client-godot/evidence/boot/boot-report.json` is regenerated by the verification run (provenance refresh, committed as a `test:` commit per established convention).
- Read-only inputs: `tests/fixtures/godot-compatibility-boot/`, `packages/game-content/`, `tools/asset-registry/*`, `assets/converted/**`, legacy sources and M4/M5 evidence (SHA-256 guards unchanged).
- No compatibility-API, transport, persistence, or content-package behavior changes; no new dependencies; execution stays on loopback under the pinned engine and interpreter.
