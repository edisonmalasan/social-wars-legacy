# Proposal

## Why

The Compatibility API v0 bootstrap already delivers a server epoch: every envelope carries `server_time` (legacy `engine.timestamp_now()`, embedded in the original page as the `serverTime` FlashVar), and `BootData` parses it into the typed save list — but the client discards it, so no foundation system can observe game time at all. Roadmap §17 reserves `GameClock` as the cross-cutting time service; with GameApi, the Compatibility API v0 bootstrap slice, ContentRegistry, and Session delivered and archived, the GameClock scaffold is the next bounded M5 objective, and later scheduled systems (production timers, cooldowns) will need server-anchored local time from it.

## What Changes

- New `GameClock` autoload (`apps/client-godot/scripts/game_clock.gd`): game time anchored to the boot response's server epoch and advanced only by local frame time — explicit `anchor(server_time) -> {ok, error}` / `clear()` lifecycle with fail-closed validation, independent `pause()` / `resume()` / `advance(msec)` controls for deterministic time, typed getters (`is_anchored`, `is_paused`, `server_time`, `elapsed_msec`, `now_epoch_sec`), and transition/advance signals; no wall-clock reads, no transport, no implicit anchor at startup.
- Boot integration: the boot scene clears any previous anchor before each attempt and anchors the clock to the successful response's `server_time` immediately before session activation, so ready implies an anchored clock and a failed boot can never leave a stale anchor behind.
- New headless suite `tests/test_game_clock.gd` wired into `verify-boot.ps1`'s hermetic list (scaffold lifecycle plus an in-process success→failure boot pair), and boot-scene assertions extended to cover the clock at ready and after failures.
- Project scope grows: `project.godot` declares a fourth autoload; `test_project_scope.gd` allow-lists the two new files, expects exactly four autoloads, and drops the `GameClock` forbidden token (17 → 16) while every other forbidden enumeration (camera, UI foundation, legacy protocol, non-loopback transport) stays forbidden.
- Documentation: `AGENTS.md`, `apps/client-godot/README.md`, and boot-verification docs record the executed commands and suite counts; the roadmap Project Status ledger is updated at archive time.

## Capabilities

### New Capabilities

- `godot-game-clock`: the GameClock autoload scaffold — server-anchored game time with a fail-closed anchor/clear lifecycle, deterministic pause and manual-advance controls, boot-scene integration that anchors and clears the clock, and containment of the grown project scope.

### Modified Capabilities

- `first-render-in-godot`: requirement R1 "Minimal render-verification Godot project" — the foundation allow-list grows to include the `GameClock` autoload with its script and tests, the project declares exactly four allow-listed autoloads (`GameApi`, `ContentRegistry`, `Session`, `GameClock`), and the forbidden enumeration drops `GameClock` while camera and UI foundation remain absent.

## Impact

- New files: `apps/client-godot/scripts/game_clock.gd`, `apps/client-godot/tests/test_game_clock.gd`.
- Modified files: `apps/client-godot/project.godot` (fourth autoload), `apps/client-godot/scripts/boot.gd` (clear/anchor integration), `apps/client-godot/tests/test_boot_scene.gd` (clock assertions at ready and on failure), `apps/client-godot/tests/test_project_scope.gd` (allow-list, four-autoload expectation, forbidden-token list), `apps/client-godot/verify-boot.ps1` (hermetic suite + report wiring), `apps/client-godot/README.md`, `AGENTS.md`, and the roadmap Project Status ledger at archive time.
- Evidence: `apps/client-godot/evidence/boot/boot-report.json` is regenerated by the verification run (provenance refresh, committed as a `test:` commit per established convention).
- Read-only inputs: `tests/fixtures/godot-compatibility-boot/`, `packages/game-content/`, `tools/asset-registry/*`, `assets/converted/**`, legacy sources and M4/M5 evidence (SHA-256 guards unchanged).
- No compatibility-API, transport, persistence, or content-package behavior changes; no new dependencies; execution stays on loopback under the pinned engine and interpreter.
