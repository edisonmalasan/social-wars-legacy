# Legacy investigation: resources

Status: **investigation complete; two concrete, evidence-backed gaps identified, and one
scope boundary recorded.** This record exists so the next bounded M7 change —
*resources* — is proposed against verified evidence rather than a guess.

This is the tenth M7 deliver line's investigation, following the same
investigation-first pattern as upgrade (`docs/legacy-construction-timing.md`),
collect income (`docs/legacy-collect-income.md`), and town expansion
(`docs/legacy-town-expansion.md`).

## Why this line exists at all

Every delivered line so far moves resources correctly *server-side*: the unchanged
legacy `apply_resources` applies the client-sent 8-slot vector verbatim per resource
as `max(current + delta, 0)` (`engine.py:251-271`), the collect line derives its
payout from committed content, and the expand line derives its debit and refuses an
uncovered balance. The M7 exit criterion — "core town-building gameplay loop works" —
additionally requires the player to *see* their resources. That is where the gaps are,
and they are not speculative: they are two rows of a committed table.

## The established resource model

The server's seven named resources, and where each one lives in the save:

| Slot | Resource | Stored at | Established by |
| --- | --- | --- | --- |
| 0 | *unread* | — | the vector's slot 0 is read and discarded; the legacy comment at `engine.py:252` names it as the cheat-detection slot |
| 1 | `xp` | `maps[0].xp` | `apply_resources` |
| 2 | `gold` | `maps[0].gold` | `apply_resources` (`engine.py:259-267`) |
| 3 | `wood` | `maps[0].wood` | `apply_resources` |
| 4 | `oil` | `maps[0].oil` | `apply_resources` |
| 5 | `steel` | `maps[0].steel` | `apply_resources` |
| 6 | `cash` | `playerInfo.cash` | `apply_resources` |
| 7 | `mana` | `privateState.mana` | `apply_resources` |

The committed corpus agrees exactly: `xp 4`, `gold 2000`, `wood 2000`, `oil 2000`,
`steel 2000`, `cash 5`, `mana 0`. The Compatibility API's `resources` accessor
(`compat_legacy.py`) returns exactly these seven keys, with the same sources, and its
docstring states that it covers "every slot `engine.apply_resources` writes".

**So the server-side model is established, consistent, and already exposed.** This
line is not about the model; it is about the projection.

## Gap 1 — the HUD's primary currency row reads a field nothing provides

`apps/client-godot/scripts/town/town_hud.gd` declares a ten-row display table, and its
first two resource rows are:

```gdscript
const FIELDS := [
	["coins", "resources", "Coins"],
	["wood", "resources", "Wood"],
	["steel", "resources", "Steel"],
	["oil", "resources", "Oil"],
	["cash", "resources", "Cash"],
	["energy", "resources", "Energy"],
	["mana", "resources", "Mana"],
	["name", "summary", "Name"],
	["level", "summary", "Level"],
	["xp", "summary", "XP"],
]
```

**There is no `coins` resource.** The server's field is `gold` (`maps[0]` has `gold`
and no `coins`), the Compatibility API's `resources` accessor returns `gold` and has
no `coins` accessor at all, and the module's only two occurrences of the word `coins`
are *comments about the expansion price schedule* (`compat_legacy.py:453,456`), not a
resource. The HUD is fail-closed by design and renders an explicit
`[missing: <field>]` indicator for an absent field — so the player's **primary
currency is displayed as missing and its real value never appears on screen**.

The existing test pins the defect rather than catching it: the crafted payload in
`apps/client-godot/tests/test_town_hud.gd:29-30` supplies `"coins": "2000"` and
`"energy": "50"` as if the bootstrap provided them, and the suite then asserts the
`Energy:` row renders `Energy: 50`. Those assertions pass against a payload shape
nothing real produces.

## Gap 2 — `energy` is a real eighth resource with no delivered accessor

`energy` is not a phantom. It is committed in three places:

- the corpus save: `privateState.energy = 50`;
- `constants.py:899`: `COST_ENERGY = "e"` — the item-cost key for energy, alongside
  the other cost letters;
- `constants.py:1054`: `TOKEN_ENERGY = 7`, and `constants.py:74`: `CAT_ENERGY = 8`.

But **`engine.apply_resources` never writes it**, the 8-slot vector has no slot for
it, and `compat_legacy.py` has no energy accessor. So the HUD's `energy` row also
renders as missing — and the resource is genuinely part of the game's economy
(`costs` may name it) while being outside every delivered surface.

Two readings are possible and the repository does not decide between them: energy may
be time-regenerated by a rule no committed source records (the legacy server has no
branch for it at all), or it may be maintained entirely on the Flash client. **No
commitment should be made either way.** The honest deliverable is to expose what the
save actually contains under its own name, and to record the regeneration rule — or
its absence — as a named gap.

## Scope boundary recorded

Two resource-adjacent systems exist and are explicitly **out of scope** for this line,
because neither is a resource projection:

- **The market and trade counters.** `trade_resource` and `set_resource_allies` exist
  (`docs/legacy-protocol/commands.md`, "Economy and trade"), and the corpus carries
  `numTradesDone 0`, `timestampLastTrade 0`, `resourcesTraded {}`, and
  `resourceAlliesMarket ""`. Note the catalogued finding that `trade_resource`'s two
  arguments are **read but unused** and it only increments the counter — so the
  trade's resource movement is client-sent, the same untrusted pattern the collect and
  expand lines already refuse to accept. Trade is a market feature, not a projection,
  and belongs to a later milestone.
- **Item costs.** `items[].costs` uses the *letter* vocabulary `g`/`c`/`w`/`o`/`s`
  (and `constants.py` names `e` for energy), which is the same second naming layer the
  expand investigation recorded. Mapping it onto the seven (now eight) named resources
  is inventory/shop work.

## What the next change should deliver

The smallest coherent, evidence-complete version of "resources":

- **A canonical, single-source resource projection** in the client, naming the seven
  server resources by the names the server actually uses (`gold`, never `coins`), with
  `xp` kept distinct from the six spendable resources because it is the experience
  counter, not a currency;
- **`gold` displayed by value** — the HUD's first row corrected from `coins` to `gold`,
  so the primary currency becomes visible for the first time;
- **`energy` exposed under its own name** with the regeneration rule recorded as an
  explicit gap, rather than left as a phantom row;
- **no duplicate rows and no invented resources** — the projection is exactly what the
  save carries, with the fail-closed missing-field behaviour preserved for anything
  genuinely absent;
- **the corrected tests** — the crafted payload gains the field names the real
  bootstrap produces, and a new assertion pins that `gold` renders its real value and
  that the row is no longer keyed `coins`;
- **no change to any delivered line's behaviour** — this is a read-only projection
  fix, so placement, purchase, move, sell, store, upgrade, construction, collect, and
  expand all keep their current semantics and their suites stay green.

Non-goals: the market and trade counters, item cost mapping, energy regeneration,
server-authoritative resource validation (Server v1 / M13), any balance change, and any
new endpoint — none of the nine delivered state-mutating surfaces needs to change,
because the defect is entirely in how the client names what the server already sends.

## Resolution, after the `building-resources` proposal and Apply (2026-09-30)

Both gaps are closed, and one of the change's own premises was wrong.

### Gap 1 — closed, and it was exactly one key

`town_hud.gd`'s `FIELDS` const is gone; the readout now projects through the new
single-source `scripts/town/resource_projection.gd`, whose primary-currency row is
named **`gold`** — the field `apply_resources` writes and the corpus stores. A reading
from the investigation turned out to make the fix obviously minimal: the table's own
header named the intended set as "coins, wood, steel, oil, cash, energy, mana", which
is **exactly** the table's ten-row shape (seven resource rows plus `name`, `level`,
`xp`). So the table was never mis-shaped — one key was misnamed. No row was added,
removed, or reordered, and the captured readout now renders every row by value:
`Gold: 2000, Wood: 2000, Steel: 2000, Oil: 2000, Cash: 5, Energy: 50, Mana: 0,
Name: Warrior, Level: 1, XP: 4`, with **no** absent-field indicator.

The suite that had pinned the defect is corrected: its crafted payload now uses the
field names the service actually produces (`gold`, `energy`) instead of the fabricated
`coins`, and new assertions pin that `gold` renders its real stored value, that no row
is keyed `coins`, that `energy` renders its stored value, and that a genuinely absent
resource still renders the explicit absent-field indicator without affecting other
rows.

### Gap 2 — closed, and the design's premise about it was wrong

The change's design assumed the stored energy value had to be **added to the service**,
because `apply_resources` never writes it and no accessor exposed it. **Apply
established the premise was false.** `TownState.RESOURCE_FIELDS` already maps
`energy` to `privateState.energy`, the delivered payload already carries the value,
and the capture renders `Energy: 50` — so the row was only ever unsourced *in the
display table*, never absent from the data.

Consequently **the Compatibility API is not modified at all**: no accessor, no
response field, no route, no error-table row, and no widening of the shared
`resources()` accessor that all nine state-mutating endpoints' value-level
post-execution proofs compare. The change is entirely client-side, which is the
narrowest possible response to a client-side defect. The narrowing reasoning is
retained in design D4 as the documented reason the shared accessor stays untouched,
and the change was narrowed rather than implemented as designed.

The regeneration gap is unchanged and still unclaimed: no committed source records
how `privateState.energy` changes over time, `apply_resources` never writes it, the
eight-slot mutation vector has no slot for it (its vector slot is recorded as `-1`),
and no legacy branch touches it. The readout displays the stored value and the report
records the absence.

### One residual misnomer, recorded rather than widened over

`TownState.Resources` still declares `var coins` with `RESOURCE_FIELDS["coins"] =
"map.gold"`. **No readout row is keyed by it** — the projection is the single place
that knows, and each row records its own typed-state field. Retiring the internal
name would touch nine further `state.resources.coins` sites plus `state.missing`, so
it is left as a separate correction rather than folded into this one.

### Evidence consequence, sanctioned and bounded

The label correction invalidated two committed M6 evidence artifacts, because
`evidence/town/report.json`'s `hud` block is produced by `hud.displayed_fields()`. They
were regenerated — sanctioned for exactly this case — and `evidence/town/report.json`
differs **only** in the two `hud` blocks, where the key moves from `coins` to `gold` in
both the fresh and slice views. No count, digest, projection constant, camera, or
selection block changed. Leaving them stale would have broken the M6 deliverable's
claim that rerunning the report step reproduces its committed bytes.
