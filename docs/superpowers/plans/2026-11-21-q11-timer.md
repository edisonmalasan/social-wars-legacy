# Q11 Timer Enforcement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enforce Q11's 240-second timer from the authoritative server clock, so an expired mission cannot be completed or rewarded; record army-wipe defeat as a remaining simulator-dependent fidelity boundary.

**Architecture:** Reuse the pure rules `tickQuest`/`isQuestDefeat`. Stamp a server-owned start/last-tick timestamp on `ActiveQuestState`; advance time at quest actions and before `end_quest` using the injected `deps.now()` — no background timer, no client clock, no client-reported result. Refuse and pay nothing on a recorded loss.

**Tech Stack:** TypeScript, Node test runner, native quest endpoints.

**Spec:** `docs/GOAL.md` (autonomous roadmap), `docs/ROADMAP.md` Group E/G4, `re/docs/12-quest-system.md` Q11.

## Global Constraints

- Server owns time and outcome; the client cannot accelerate or declare a loss/win.
- No positional simulator is introduced; army-wipe defeat stays documented as not enforced.
- Pure rules engine stays pure; time comes only from `deps.now()`.
- No client clock trust, no fabricated win/loss, no weakened check, no 94-command catalogue change.
- Idempotent tick/retry; no reward on loss, duplicate or replay; 401-item roadmap accounting unchanged.

## Review Focus

- An expired Q11 action/end_quest is refused with unchanged wallet and no award.
- A non-expired quest is unaffected; time advancement is monotonic and idempotent.
- The rules' `result`/`isQuestDefeat` contradiction for Q11 immediate resolution is reconciled without changing other quests' behaviour.
- Army-wipe defeat is not falsely claimed.
